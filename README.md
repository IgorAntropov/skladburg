# Тридок

Тридок — рабочее название продукта, репозиторий и пакеты называются `skladburg`. Это B2B-платформа поставок трёх сторон — поставщика, заказчика и перевозчика — с полноценной WMS внутри, в стиле изометрического симулятора: склады, двор, машины и сделки — в живом мире вместо таблиц. Сейчас проект — демо для инвесторов: оно работает прямо в браузере и публикуется на GitHub Pages.

## Требования

- Node 24 LTS (версия указана в `.nvmrc`).
- git: при первой установке из репозитория GitHub загружается `validate.proto` с правилами проверки контракта.
- pnpm через Corepack: он входит в Node 24, а версию pnpm Corepack берёт из поля `packageManager` сам. В Node 25 и новее Corepack ставится отдельно: `npm i -g corepack`.

## Запуск

```bash
nvm use
corepack enable
pnpm install
pnpm dev
```

Приложение откроется на `http://localhost:5173/skladburg/`: так же, как на GitHub Pages, под путём `/skladburg/`. Корень `http://localhost:5173` перенаправляет туда сам.

`pnpm install` также генерирует типы контракта API. При первой установке нужен доступ к GitHub, дальше генерация берётся из кеша turbo.

`pnpm install` сам ставит git-хук pre-commit: перед коммитом ESLint и поиск комментариев проверяют изменённые файлы (lint-staged), затем запускаются все тесты.

## Сквозные тесты

Браузеры Playwright (chromium и webkit, около 500 МБ в кеше) ставятся один раз:

```bash
pnpm --filter @skladburg/web exec playwright install chromium webkit
```

Дальше `pnpm e2e` сам собирает приложение, поднимает превью на `http://localhost:4174/skladburg/` и прогоняет сценарии в обоих браузерах. HTML-отчёт остаётся в `apps/web/playwright-report`.

## Замер первого экрана

Инструмент снимает, как быстро появляется первый экран с данными: холодный старт (чистый браузер, 7 прогонов) и тёплый (после первой загрузки, до 5 прогонов) на трёх профилях: телефон на «Fast 4G», телефон на медленной сети и компьютер. Перед серией каждого профиля идёт один прогревочный холодный прогон, его результат отбрасывается, поэтому серия длится дольше, чем кажется. В `pnpm e2e` и CI замер не входит.

Сеть и процессор замедляются через Chrome DevTools Protocol. Сеть действует на запросы страницы и Worker движка (строка «Worker под троттлингом» судит по времени загрузки ядра движка самим Worker; если Worker взял ядро из кеша, потому что его заранее загрузила подсказка в документе, строка читается «неприменимо»), процессор — только на основной поток: на Worker замедление CPU не применяется, и движок в Worker быстрее реального телефона. Загрузки service worker (precache) считаются отдельно, цифры страницы и Worker их не включают. Замедляются они своей эмуляцией на цели service worker, а не общим каналом со страницей: две параллельные загрузки не делят полосу (проверено отдельным опытом), поэтому конкуренция precache с критическим путём моделируется не полностью, а оценивать её нужно по строкам «Service worker: … до готовности». Окно замера кончается через 1,5 с после готовности, precache за него успевает лишь начаться, так что список повторных загрузок service worker — нижняя оценка. Строка «Service worker под троттлингом» в отчёте: «да» — эмуляция принята во всех холодных прогонах; «нет» или «частично» — в части прогонов браузер отказал или первые загрузки service worker (быстрее 0,8 × задержки профиля) прошли до эмуляции; «не определено» — подготовка эмуляции не завершилась к снимку (инструмент ждёт её до секунды); «неприменимо» — service worker не появился. Прогоны-исключения перечислены под строкой с причиной. В тёплых прогонах цель service worker своих сетевых запросов не показала, поэтому проверка обновления `sw.js` в отчёт не попадает.

Сначала собери приложение, затем запусти замер. Он сам поднимет превью сборки на `https://localhost:4175/skladburg/` с заголовком `Cache-Control: max-age=600`, как на GitHub Pages, и с HTTP/2: на Pages все запросы идут по одному соединению, а на HTTP/1.1 часть запросов ждёт в очереди и показывает слишком оптимистичную картину:

```bash
pnpm --filter @skladburg/web build
pnpm --filter @skladburg/web perf
```

Таблица медиан печатается в консоль в конце прогона. Превью обязано отдавать `Cache-Control: max-age=600`, иначе замер прервётся с ошибкой. Если прогон не дошёл до готового первого экрана за 90 секунд, он записывается без готовности, остальные метрики сохраняются, серия продолжается. В шапке отчёта для превью указаны протокол документа, сборка (`git describe --always --dirty`) и время изменения `dist/index.html`. Переменные окружения:

| Переменная                        | Что задаёт                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `PERF_BASE_URL`                   | внешний адрес вместо превью, например `https://igorantropov.github.io/skladburg/`                      |
| `PERF_PROFILES`                   | профили через запятую: `mobile-fast-4g`, `mobile-slow-4g`, `desktop-fast-4g` (по умолчанию все три)    |
| `PERF_RUNS`                       | число холодных прогонов, по умолчанию 7; тёплых — столько же, но не больше 5                           |
| `PERF_REPORT_FILE`                | путь к Markdown-отчёту, от `apps/web` или абсолютный; JSON сырых прогонов — рядом, `.json`             |
| `PERF_PREVIEW_PROTOCOL`           | `h2` (по умолчанию) или `h1`: превью по HTTPS с HTTP/2 или по HTTP/1.1, как замеры до шага 1.10b3      |
| `PERF_PAGES_SKELETON_BASELINE_MS` | скелетон «до» на Pages без подсказок (972 для v2); с ним в отчёте появляется «Прогноз скелетона Pages» |

**Сертификат для HTTP/2.** Vite поднимает HTTP/2 только по HTTPS. Если заданы `DEV_HTTPS_CERT_FILE` и `DEV_HTTPS_KEY_FILE` (окружение или `apps/web/.env.local`, раздел ниже), замер берёт их. Иначе системный `openssl` выпускает временный самоподписанный сертификат в `apps/web/test-results/perf-tls/` (в git он не попадает) и переиспользует его в следующих запусках; нет `openssl` и переменных — замер остановится с подсказкой, обойти можно `PERF_PREVIEW_PROTOCOL=h1`. Браузер замера доверяет сертификату по отпечатку его публичного ключа (`--ignore-certificate-errors-spki-list`), а не отключает проверку: Chrome не кеширует ответы с ошибкой сертификата, и без этого подсказки в документе не доходили бы до Worker. Протокол ответа документа читается из CDP; при `h2` и другом ответе замер падает с понятным сообщением. Для внешнего адреса протокол только записывается в шапку.

**Метрики от входного скрипта.** Задержка ответа сервера (TTFB у CDN плавает на десятки миллисекунд) не зависит от кода приложения, поэтому рядом с абсолютными временами есть метрики от начала запроса входного скрипта `index-*.js`: «Старт запроса входного скрипта», «Скелетон от старта входного скрипта» (`skeletonFromEntry`) и «Первый экран от старта входного скрипта» (`firstScreenFromEntry`). Входной скрипт — первый `<script type="module" src>` документа; если страница его не назвала, ищется первый запрос `/assets/index-*.js`.

**Дележ канала.** Эмуляция сети CDP делит полосу между активными запросами поровну и не учитывает `fetchpriority`, поэтому всё, что идёт параллельно с входным скриптом, замедляет его. Строка отчёта «Дележ канала с входным скриптом: N КБ параллельно, оценка задержки ≈ M мс» — медиана по холодным прогонам суммы `min(размер запроса, размер входного скрипта)` по запросам страницы и Worker, у которых первый байт (старт запроса плюс задержка профиля) мог прийти до конца входного скрипта (без самого скрипта, CSS, документа, ответов из кеша и перепроверок), делённой на полосу приёма профиля. CSS не входит: он шёл вместе со скриптом и до подсказок. С `PERF_PAGES_SKELETON_BASELINE_MS` для `mobile-fast-4g` добавляется строка «Прогноз скелетона Pages ≈ база + M мс». Это оценка по модели равной доли, а не замер.

**Перепроверки (304).** На превью Chromium шлёт условный запрос за верхним скриптом выделенного Worker, хотя тот свежий в кеше: сервер отвечает 304 за один круг, тело берётся из кеша. На Pages такой перепроверки нет, причина не найдена, поэтому первый экран на превью завышен примерно на круг до сервера. Такие запросы находятся по записям Resource Timing (сопоставляются с запросами CDP по адресу и времени старта; `transferSize` меньше `encodedBodySize`) и помечены `isRevalidated`. Они попадают в водопад отдельной строкой, в список «Перепроверки (304) до готовности» (`revalidatedBeforeReady`), но не в дубли, запросы и байты до готовности. В JSON, снятых прежней версией инструмента, перепроверок нет, и восстановить их нельзя.

## Телефон в локальной сети по HTTPS

Камера и service worker работают только по HTTPS, а `localhost` Мака телефон не видит. Чтобы открыть дев-сервер или превью на iPhone и iPad, нужен доверенный сертификат. Его выпускает mkcert, в проект ничего не ставится. Без переменных ниже всё остаётся как было: `http://localhost`.

На Маке, один раз:

```bash
brew install mkcert
mkcert -install
scutil --get LocalHostName
ipconfig getifaddr en0
mkdir -p ~/.config/skladburg-dev-cert
mkcert -cert-file ~/.config/skladburg-dev-cert/dev.pem -key-file ~/.config/skladburg-dev-cert/dev-key.pem <имя-мака>.local <IP-мака> localhost
```

`scutil` печатает имя Мака, `ipconfig` — его IP в сети (`en0` — Wi-Fi; если сеть по кабелю, интерфейс другой). Для Firefox перед `mkcert -install` нужен ещё `brew install nss`. Если IP Мака сменится, сертификат выпускается заново.

Файл `apps/web/.env.local` (в git он не попадает):

```
DEV_HTTPS_CERT_FILE=/Users/<логин>/.config/skladburg-dev-cert/dev.pem
DEV_HTTPS_KEY_FILE=/Users/<логин>/.config/skladburg-dev-cert/dev-key.pem
```

Нужны обе переменные: если задана одна или файл не читается, сервер не стартует и называет переменную. Корневые `pnpm dev` и `pnpm preview` идут через Turborepo и не передают неизвестные переменные окружения, поэтому для них значения берутся только из `apps/web/.env.local`. Переменные окружения работают лишь при запуске напрямую, например `pnpm --filter @skladburg/web dev`: там они перекрывают файл. При заданных переменных дев-сервер и превью работают по HTTPS и доступны из сети.

На iPhone и iPad, один раз:

1. Отправить корневой сертификат `$(mkcert -CAROOT)/rootCA.pem` на устройство через AirDrop.
2. Установить профиль: Настройки → Основные → VPN и управление устройством.
3. Включить полное доверие: Настройки → Основные → Об этом устройстве → Доверие сертификатам.

Адреса:

- `https://<имя-мака>.local:5173/skladburg/` — `pnpm dev`, без service worker;
- `https://<имя-мака>.local:4173/skladburg/` — `pnpm build && pnpm preview`, со service worker: так проверяются установка, офлайн и обновление.

После смены пути на `/skladburg/` один раз удалите старый service worker с `localhost:4173` и `<имя-мака>.local:4173` (DevTools → Application → Service workers → Unregister) и установленное с превью приложение на телефоне, иначе они продолжат отдавать прежнюю сборку.

Чтобы вернуться на `http://localhost`, достаточно убрать переменные из `apps/web/.env.local`.

## Публикация

Демо публикуется на GitHub Pages по адресу `https://igorantropov.github.io/skladburg/`. Каждый push в `main` запускает GitHub Actions (`.github/workflows/pages.yml`): сначала `pnpm lint`, `pnpm test` и `pnpm build`, затем, если всё зелёное, сборка из `apps/web/dist` уходит на Pages. Запустить публикацию можно и вручную со вкладки Actions.

Один раз в репозитории: Settings → Pages → Build and deployment → Source — GitHub Actions.

Тексты лицензий сторонних пакетов, которые попали в сборку, лежат рядом с приложением: `https://igorantropov.github.io/skladburg/third-party-licenses.txt`. Сборка падает, если лицензия пакета не из разрешённых или у пакета нет текста лицензии. Запасные тексты для пакетов без собственного файла лежат в `apps/web/build-licenses/fallback-texts/`.

## Структура

- `apps/web` — приложение на Vite и React. В `src` лежат слои Feature-Sliced Design: сейчас `app`, `pages` и `shared`. Сквозные тесты Playwright лежат в `e2e`.
- `packages/contracts` — контракт API: `.proto` — источник типов, `src/gen` генерируется и не коммитится.
- `packages/demo-engine` — «платформа в браузере»: движок демо без сервера (организации, права, события и общие данные на стартовых заглушках), говорит на том же протоколе Connect, что и будущий бэкенд, и не зависит от React и DOM.
- `scripts` — проверки репозитория (правила ESLint, поиск комментариев) и их тесты.

## Контракт API

Контракт лежит в `packages/contracts/proto/<модуль>/v1/<файл>.proto`. Типы и описания сервисов генерируются командой `pnpm proto:generate` (она же запускается при `pnpm install`) в `packages/contracts/src/gen`; эта папка и `proto-deps` в git не попадают, руками их не правят. Типы импортируются по пути `@skladburg/contracts/<модуль>/v1/<файл>`, например `@skladburg/contracts/common/v1/error`. Комментарии в `.proto` не пишутся: смысл несут имена и правила `buf.validate`.

## Профили сборки и языки

Набор языков в сборке и компания по умолчанию (название, языки, термины) задаются профилем сборки. Профили лежат в `apps/web/profiles/<имя>.json`, по умолчанию берётся `default`:

```bash
BUILD_PROFILE=<имя> pnpm build
BUILD_PROFILE=<имя> pnpm dev
```

Профиль содержит:

- `bundledLocales` — языки, каталоги которых попадают в сборку; каталоги остальных языков в неё не входят;
- `defaultTenant` — компания по умолчанию: `tenantId`, `brandName` (он же `<title>` страницы), `availableLocales`, `defaultLocale` и `termOverrides` — переопределения текстов интерфейса по языкам.

Язык `<html lang>` и заголовок страницы при сборке берутся из профиля, в работе приложения — из активного языка и названия компании. Коды языков записываются в канонической форме BCP 47 (`ru`, `en`, `ru-RU`): неверный тег или регистр (`RU`, `ru-ru`) — ошибка сборки. Каталог языка по умолчанию входит в основной бандл, остальные языки профиля грузятся отдельными файлами. Ошибки в профиле (нет файла, пустой список языков, нет каталога языка, `defaultLocale` вне списков) останавливают сборку с понятным сообщением.

### Как добавить язык

1. Создать каталог `apps/web/src/shared/i18n/catalogs/<язык>.ts` с именованным экспортом `catalog`, объявленным как `as const satisfies LocaleCatalogValue` (тип из `@/shared/i18n`). Те же ключи, что в `ru.ts`; у сообщений во множественном числе — все формы языка. Недостающий ключ — ошибка проверки типов; недостающая форма множественного числа — ошибка теста полноты каталогов.
2. Добавить язык в `bundledLocales` нужного профиля и в `defaultTenant.availableLocales`.

Строки интерфейса живут только в каталогах: в разметке (`*.tsx`) текст и пользовательские атрибуты (`title`, `aria-label`, `placeholder`, `alt` и другие) берутся через `t('<ключ>')`, это проверяет `pnpm lint`. Числа, валюта и даты форматируются через `useI18n()` (`formatNumber`, `formatCurrency`, `formatDate`).
