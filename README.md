# Тридок

Тридок — рабочее название продукта, репозиторий и пакеты называются `skladburg`. Это B2B-платформа поставок трёх сторон — продавца, покупателя и логиста — с полноценной WMS внутри, в стиле изометрического симулятора: склады, двор, машины и сделки — в живом мире вместо таблиц. Сейчас проект — демо для инвесторов: оно работает прямо в браузере и публикуется на GitHub Pages.

## Требования

- Node 24 LTS (версия указана в `.nvmrc`).
- git: при первой установке из репозитория GitHub загружается `validate.proto` с правилами проверки контракта.
- pnpm через Corepack: он входит в Node 24, а версию pnpm Corepack берёт из поля `packageManager` сам. В Node 25 и новее Corepack ставится отдельно: `npm i -g corepack`.

## Запуск

```bash
nvm use
corepack enable
pnpm install
pnpm dev
```

Приложение откроется на `http://localhost:5173`.

`pnpm install` также генерирует типы контракта API. При первой установке нужен доступ к GitHub, дальше генерация берётся из кеша turbo.

`pnpm install` сам ставит git-хук pre-commit: перед коммитом ESLint и поиск комментариев проверяют изменённые файлы (lint-staged), затем запускаются все тесты.

## Скрипты

| Команда               | Что делает                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `pnpm dev`            | dev-сервер Vite с горячей перезагрузкой                                                       |
| `pnpm build`          | проверка типов и production-сборка                                                            |
| `pnpm preview`        | локальный просмотр production-сборки                                                          |
| `pnpm test`           | все unit-тесты: проверки репозитория, контракт и приложение                                   |
| `pnpm lint`           | проверка типов, архитектуры слоёв, `buf lint` и формата `.proto`, ESLint и поиск комментариев |
| `pnpm lint:fix`       | автоисправление ESLint и форматирование `.proto` (`buf format`)                               |
| `pnpm typecheck`      | проверка типов по всему монорепозиторию                                                       |
| `pnpm proto:generate` | генерация типов и образа контракта из `.proto`                                                |

## Структура

- `apps/web` — приложение на Vite и React. В `src` лежат слои Feature-Sliced Design: сейчас `app`, `pages` и `shared`.
- `packages/contracts` — контракт API: `.proto` — источник типов, `src/gen` генерируется и не коммитится.
- `packages/demo-engine` — «платформа в браузере»: движок демо без сервера (организации, права, события и общие данные на стартовых заглушках), говорит на том же протоколе Connect, что и будущий бэкенд, и не зависит от React и DOM.
- `scripts` — проверки репозитория (правила ESLint, поиск комментариев) и их тесты.

## Контракт API

Контракт лежит в `packages/contracts/proto/<модуль>/v1/<файл>.proto`. Типы и описания сервисов генерируются командой `pnpm proto:generate` (она же запускается при `pnpm install`) в `packages/contracts/src/gen`; эта папка и `proto-deps` в git не попадают, руками их не правят. Типы импортируются по пути `@skladburg/contracts/<модуль>/v1/<файл>`, например `@skladburg/contracts/common/v1/error`. Комментарии в `.proto` не пишутся: смысл несут имена и правила `buf.validate`.

## Профили сборки и языки

Набор языков в сборке и компания по умолчанию (название, языки, термины) задаются профилем сборки. Профили лежат в `apps/web/profiles/<имя>.json`, по умолчанию берётся `default`:

```bash
BUILD_PROFILE=<имя> pnpm build
BUILD_PROFILE=<имя> pnpm dev
```

Профиль содержит:

- `bundledLocales` — языки, каталоги которых попадают в сборку; каталоги остальных языков в неё не входят;
- `defaultTenant` — компания по умолчанию: `tenantId`, `brandName` (он же `<title>` страницы), `availableLocales`, `defaultLocale` и `termOverrides` — переопределения текстов интерфейса по языкам.

Язык `<html lang>` и заголовок страницы при сборке берутся из профиля, в работе приложения — из активного языка и названия компании. Коды языков записываются в канонической форме BCP 47 (`ru`, `en`, `ru-RU`): неверный тег или регистр (`RU`, `ru-ru`) — ошибка сборки. Каталог языка по умолчанию входит в основной бандл, остальные языки профиля грузятся отдельными файлами. Ошибки в профиле (нет файла, пустой список языков, нет каталога языка, `defaultLocale` вне списков) останавливают сборку с понятным сообщением.

### Как добавить язык

1. Создать каталог `apps/web/src/shared/i18n/catalogs/<язык>.ts` с именованным экспортом `catalog`, объявленным как `as const satisfies LocaleCatalogValue` (тип из `@/shared/i18n`). Те же ключи, что в `ru.ts`; у сообщений во множественном числе — все формы языка. Недостающий ключ — ошибка проверки типов; недостающая форма множественного числа — ошибка теста полноты каталогов.
2. Добавить язык в `bundledLocales` нужного профиля и в `defaultTenant.availableLocales`.

Строки интерфейса живут только в каталогах: в разметке (`*.tsx`) текст и пользовательские атрибуты (`title`, `aria-label`, `placeholder`, `alt` и другие) берутся через `t('<ключ>')`, это проверяет `pnpm lint`. Числа, валюта и даты форматируются через `useI18n()` (`formatNumber`, `formatCurrency`, `formatDate`).
